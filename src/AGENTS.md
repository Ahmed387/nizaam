# Frontend rules

- New-document recipient is the signed-in user via `LockedRecipientInput` and stays read-only.
- Render list-level `#` columns through `DataTable.indexColumn` as 1-based numeric indices with the correct server-page offset — why: numbering stays consistent and continuous across pagination.
- Derive treasury labels with format helpers; never rewrite stored ledger text.
- Every statistical card uses `MetricHint` with meaning, source, and exact formula.
- Wide tables use DataTable `minTableWidth` (wrapper gets `data-wide`); `index.css` compact CSS stays `:not([data-wide])`-guarded.
- The six document tabs in `Invoices.tsx` use `UnifiedDocumentFilters` + `UnifiedDocumentMetrics`; card values and click-to-filter both come from `docFacts` in `lib/documentMetrics.ts` — why: one formula per card, cards and table never diverge.
- Every document contact picker uses `ContactLookup` → `search_branch_contacts` RPC: every customer / supplier of the company (not archived, type + both), own branch first, paged 50 at a time while scrolling, any letter filters on the server (name / phone); other branches' contacts show their branch name — why: owner rule (0085), one picker everywhere, no 1,000-row cap.
- The sale / purchase cancel dialogs use `CancelMoneyChoice` with `document_cancel_preview`: one question about the money paid ON the document (credit / refund with method / void) — why: owner rule (0085).
- The Contacts page reads through the `contacts_page` RPC (search, type tab, balance filter, paging, counts and totals in one jsonb result) — why: all contacts searchable, no 1,000-row cap.
- An automatic voucher carries its document's notes (" — ملاحظات: …" after its own text) and the document's recipient when it has none (migration 0087): filled on insert, on the plan link, and again whenever the document's notes / recipient change (`doc_notes_to_vouchers_trg`); text only — amounts, dates, till and ledger untouched.
- `cancel_sale_return`'s guard uses the alias `gr` (the alias `r` clashed with its record variable and made every sale-return cancel fail) — migration 0088.
- «إيصال التحويل» (owner rule 2026-10-15): every payment form shows an optional receipt upload for non-cash methods (`PaymentProofInput`, inside `PaymentMethodPicker` and the custom forms); after the save `attachPaymentProofs` (src/lib/paymentProofs.ts) uploads the files to the voucher of THAT payment (record_type `voucher`, found by user / method / amount / branch since `proofClock()`). Never send the files to an RPC. Documents show `DocumentMoneyMovements` (movements count + attachments count, 📎 per voucher); treasury and the contact file show 📎 per movement.
- storage.objects policies for every bucket (record / voucher attachments, product images, employee IDs, backups) are in migration 0090 — the move off Lovable Cloud left the table with none and every upload failed with an RLS error. Uploads go to `<tenant_id>/...` with `owner = auth.uid()`.
- A past period on the sale / purchase screens is read on ONE date — its last day (owner rule 2026-10-16, migration 0091): `ledger_document_split_as_of` (via `fetchDocumentPayView`) gives the as-of status AND the method columns / card breakdown of what was paid by then; money paid after the period is a note («اتدفع بعد الفترة … من …»), never in the columns — why: PO00191 showed «لم يتم الدفع» next to «كاش 19,300».
- A purchase invoice is «نقدي» when its own plan's payments dated the invoice's own day pay it in full — also for an invoice entered later with an old date (migration 0092, `ledger_settlement_rows`); before, only a payment saved in the same 5 seconds counted — why: PO00279 / PO01224 were paid on their day and showed «آجل».
- «تحويل لنقدي / تحويل لآجل» (owner decision 2026-10-16, migration 0093) moves the MONEY, never a label: `document_class_preview` / `document_class_convert` (sale + purchase, one or many, permission `doc_class.update` — default owner / admin / branch manager). To نقدي: own later payments move to the invoice day in place (same voucher), advance uses go back to the account, the rest is a new payment dated the invoice day (method + transfer receipt); money from a general voucher / a return goes to the oldest open invoice or stays on account. To آجل: the invoice-day payments are cancelled on their day. Refused: cancelled, before 2026, closed period, a hand-over that paid other invoices, walk-in sale to آجل. Warnings: till below zero that day, a fee in a distributed period. UI: `ConvertClassDialog` from the class badge (table), the selection bar, and the money card on the invoice. A sale's own payment dated the invoice day is «with the invoice» too (`ledger_settlement_rows`).
- `settings` is per company (migration 0094): PRIMARY KEY (scope, key), scope = tenant_id (or the platform for rows without a company, e.g. project_url — read by `nizam_settings_platform_value`). Screens save through `saveCompanySetting` (src/lib/companySettings.ts, upsert on `scope,key`, throws on error) — why: one company's save used to own the key for all and others got «تم الحفظ» with nothing saved (return window 2026-10-16).
- A return's journal, refund voucher and till rows live on the return's own day (migration 0095): `return_sync_dates(kind, id)` re-dates them and trigger `zz_return_dates_sync` runs it whenever `returns` / `purchase_returns.invoice_date` changes; cancel reversals stay on the cancel day; stock_movements stays immutable (stock reports read the return date) — why: SR00070 dated 31/01 had its refund voucher and till on the entry day 16/10 (2026-10-16).
- Cancelling a return gives back only the refund still out (migration 0096): `cancel_sale_return` / `cancel_purchase_return` subtract what voiding the refund voucher already reversed («إلغاء سند») — why: SR00069 put 1,150 back in the till twice (2026-10-16).
- Document tables (sale, purchase, both returns, both voucher tabs) share one selection bar `BulkActionsBar` (src/components/documents): open as tabs (`openDocs` → `OpenDocsBar` in AppShell, max 30, vouchers open at `/branch/:id/vouchers/:voucherId`), print all in one job A4 or 80mm (`printDocuments`, src/lib/bulkPrint.ts), export the selection, edit all (notes; date for admins, with a preview of the money that moves), cancel all (returns: owner; vouchers: same rule as the row). Every write goes through the single-document RPCs one by one (`src/lib/bulkDocs.ts`), never a new bulk write path; sale / purchase invoices are not bulk-cancelled (each asks about its money). The recipient stays locked.
- Table columns follow the sale order everywhere (number · party · amount · class · paid/remaining · cash · InstaPay · wallet · bank · account · status · recipient · notes · date · actions); a column with no meaning on a screen is left out. Vouchers read what they paid from `voucher_money_split` and the till its running balance from `treasury_balance_after` (migration 0097).
