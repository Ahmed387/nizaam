# إصلاح تاريخ الفاتورة وإضافة تفاصيل الصف

## الهدف
توحيد تعديل تاريخ فاتورة البيع في مسار سيادي آمن، وإضافة سهم يعرض بنود الفاتورة داخل جدول فواتير البيع عند الطلب، دون تحميل البنود مسبقاً أو المساس بالبيانات المحمية.

## التنفيذ

### 1. دالة سيادية جديدة لتاريخ الفاتورة
- إضافة Migration جديدة فقط تُنشئ `public.update_invoice_date_sovereign(uuid, timestamptz, text)` وتمنح تنفيذها للمستخدمين المسجلين.
- رفض الطلب عند غياب جلسة مستخدم، أو غياب التاريخ، أو عدم وجود الفاتورة.
- قفل صف الفاتورة أثناء العملية والتحقق من تطابق مستأجر المستخدم مع مستأجر الفاتورة.
- السماح فقط للمالك الفعلي للمستأجر، أو دور `owner`/`admin` المرتبط بالمستأجر نفسه، أو `super_admin`، مع التحقق من صلاحية إدارة فرع الفاتورة.
- فحص التاريخ القديم والجديد ضد الفترات المالية المغلقة قبل أي كتابة.
- تحديث `invoices.invoice_date` وتاريخ قيود `journal_entries` ذات `source_id` المطابق و`source_type` من `invoice` أو `invoice_cogs` فقط، داخل معاملة RPC واحدة.
- عدم تعديل المدفوعات أو الأقساط أو الخزينة أو بنود الفاتورة أو دفعات المخزون وFIFO.
- كتابة حدث تدقيق صريح `invoice_date_changed` يحفظ التاريخين والسبب وهوية المستخدم ومعرّفات القيود، بحيث يؤدي فشل التدقيق إلى Rollback كامل.
- إبقاء التوقيعات والمسارات القديمة متاحة للتوافق التراجعي، مع تحويل واجهة تعديل التاريخ إلى المسار الجديد.

### 2. توحيد واجهة تعديل التاريخ
- تعديل `EditableInvoiceDate.tsx` لاستدعاء RPC الجديد بدلاً من UPDATE المباشر.
- تمرير السبب اختيارياً، وإظهار نص الخطأ الأصلي من قاعدة البيانات دون استبداله برسالة عامة.
- الإبقاء على تجربة التحرير الحالية وحدث `onSaved` دون تغيير للمستهلكين.

### 3. تحميل بنود الفاتورة عند التوسيع
- إضافة hook مركزي يستخدم React Query بمفتاح `['invoice-items', tenantId, branchId, invoiceId]`.
- تفعيل الاستعلام فقط عند فتح الصف، والتحقق صراحةً من `tenant_id` ومن أن الفاتورة تنتمي إلى `branch_id` المطلوب.
- جلب الحقول الضرورية فقط: اسم الصنف، الكمية، سعر الوحدة، والإجمالي الفرعي.
- ضبط مدة صلاحية cache لمنع إعادة الجلب عند غلق وفتح الصف نفسه، مع إبطال cache عند تغييرات البنود الفورية.

### 4. صف التفاصيل المدمج
- توسيع `DataTable` بخصائص اختيارية لمفتاح الصف، حالة التوسيع، ومحتوى الصف الفرعي، دون تغيير سلوك الجداول الحالية.
- إضافة سهم بجوار رقم فاتورة البيع في `Invoices.tsx`، ومنع نقر السهم من فتح صفحة الفاتورة.
- عرض صف فرعي مباشرة أسفل الفاتورة يحتوي Loader أثناء الجلب، وجدولاً صغيراً للبنود، وحالتي الفراغ والخطأ.
- قصر الخاصية على تبويب فواتير البيع؛ بقية المستندات والجداول تبقى كما هي.

## التحقق
- اختبارات قراءة/rollback للأدوار المسموحة والمرفوضة، عزل المستأجر والفرع، الفترات المغلقة، وتراجع العملية عند فشل أي خطوة.
- إثبات أن التغيير اقتصر على `invoice_date` وقيدي `invoice` و`invoice_cogs`، دون تغيير المدفوعات أو الأقساط أو الخزينة أو FIFO.
- اختبار فتح الصف، إغلاقه وإعادة فتحه للتأكد من استخدام cache وعدم تكرار الطلب.
- تشغيل فحص TypeScript و`npm run build`.
- إعادة قراءة أعداد الفروع والمنتجات والأرشيف ومصروفات وإيداعات المالك قبل وبعد التنفيذ وإعلان النتائج الفعلية.

## تفاصيل تقنية
- لن تُعدّل أي Migration قديمة، ولن تُحذف أو تُعاد كتابة سجلات مالية قائمة خارج القيود المحددة.
- لا يوجد مصدر سيريال/IMEI موثوق في `invoice_items` حالياً، لذا سيعرض الصف الحقول الأربعة المطلوبة فقط.
